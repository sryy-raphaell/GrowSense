# 3 Metode Pengembangan

## 3.1 Pendekatan SDLC yang Dipilih

GrowSense dikembangkan dengan model **Iterative and Incremental**. Pada model ini, sistem dibangun dalam beberapa iterasi, dan setiap iterasi menghasilkan inkremen yang sudah dapat dipakai serta diuji sebelum fungsi berikutnya ditambahkan (Sommerville, 2016; Pressman & Maxim, 2020). Pendekatan ini dipilih karena empat alasan yang berasal dari kondisi proyek:

1. **Perangkat keras tersedia bertahap.** Kamera, pengatur daya, panel surya, baterai, dan sensor EC dengan rentang lebih luas ditetapkan pada tahap desain dan diadakan sesuai biaya (SRS bagian 1.5 dan OTH-05). Model bertahap memungkinkan perangkat lunak dikembangkan lebih dulu pada bagian yang tidak bergantung pada komponen tersebut.
2. **Banyak nilai masih berstatus usulan.** Interval sensor, ambang keyakinan deteksi, aturan dosing, dan kapasitas daya masih perlu divalidasi (SRS Lampiran C). Setiap iterasi memberi kesempatan memvalidasi sebagian nilai itu sebelum dikunci.
3. **Risiko teknis berbeda-beda.** Deteksi YOLOv8 dan dosing adaptif berisiko lebih tinggi daripada pemantauan dasar, sehingga fondasi pemantauan dibangun dan diuji lebih dulu.
4. **Prioritas jelas.** Kebutuhan berprioritas Must dikerjakan lebih dulu, sedangkan kebutuhan Could ditunda ke tahap lanjutan (SRS bagian 2 dan OTH-05).

Perubahan terhadap SRS dikelola melalui prosedur Change Request pada SRS Lampiran B, sehingga perubahan antar-iterasi tetap terkendali dan tercatat.

## 3.3 Rencana pada Setiap Tahap SDLC

| Tahap | Rencana kegiatan | Keluaran |
| --- | --- | --- |
| Perencanaan | Menetapkan masalah, tujuan, dan batasan (problem framing); mengidentifikasi stakeholder dan cakupan; menetapkan model SDLC dan rencana iterasi; menyusun daftar risiko (komponen perangkat keras, kualitas model, biaya). | Problem framing, rencana iterasi, daftar asumsi (SRS Lampiran C) |
| Analisis | Memodelkan proses AS-IS dan TO-BE dengan BPMN; menyusun User Persona; menurunkan kebutuhan pengguna menjadi kebutuhan fungsional (FR-01 sampai FR-20) dan nonfungsional dengan prioritas MoSCoW dan kriteria penerimaan terukur; memilih tiga use case utama dan menspesifikasikannya dengan template Cockburn. | Diagram BPMN, User Persona, SRS, Use Case Specification |
| Perancangan | Merancang arsitektur empat lapisan (perangkat, AI, keputusan, aplikasi); memodelkan perilaku dengan Use Case dan Activity Diagram serta struktur domain dengan Class Diagram; menetapkan antarmuka (MQTT, JSON, HTTPS) dan skema data; menyusun RTM untuk menjamin ketertelusuran kebutuhan ke desain dan test case. | Use Case, Activity, dan Class Diagram, RTM, rancangan antarmuka |
| Implementasi | Membangun tiap iterasi sesuai rencana: firmware ESP32-S3, layanan ingest dan basis data PostgreSQL, dashboard Next.js, model YOLOv8 dan decision layer, serta modul daya. Kode dikelola dengan Git dan setiap perubahan melalui pull request (MNT-01). | Inkremen perangkat lunak dan firmware per iterasi |
| Pengujian | Menjalankan test case yang diturunkan dari kriteria penerimaan tiap FR dan cara verifikasi tiap NFR: uji meja untuk dosing, uji 24 jam untuk pembacaan dan penyimpanan, uji pemadaman terkontrol, evaluasi model (mAP@0,5), uji otorisasi dan keamanan, serta uji kegunaan dengan SUS. | Laporan uji, status test case pada RTM |
| Evaluasi dan pemeliharaan | Meninjau hasil tiap iterasi bersama stakeholder, memperbarui nilai usulan pada SRS melalui Change Request, menjadwalkan kalibrasi sensor dan pelatihan ulang model (MNT-05 dan MNT-06), lalu merencanakan iterasi berikutnya. | SRS versi baru, rencana iterasi berikutnya, panduan pemeliharaan |

Tahap Perencanaan, Analisis, dan Perancangan didokumentasikan pada laporan ini sebagai bagian Evaluasi Tengah Semester. Tahap Implementasi, Pengujian, dan Evaluasi merupakan rencana pengembangan lanjutan berdasarkan rancangan tersebut.
